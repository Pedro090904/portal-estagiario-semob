1. O que é o Git, Para que Serve e Como Pensar Nele

O Git é um Sistema de Controle de Versões Distribuído (DVCS). Em termos práticos, ele monitora cada alteração feita no código-fonte de um projeto ao longo do tempo, registrando exatamente quem alterou, quando alterou, quais linhas mudaram e qual o propósito daquela alteração.

💡 A Analogia Mental do Git

Pense no Git como uma Máquina do Tempo com Universos Paralelos e Pontos de Salvamento (Checkpoints):

  • O Checkpoint (Commit): Imagine que você está jogando um RPG difícil. Antes de entrar em uma sala perigosa, você salva o progresso. Se morrer, volta para o save exato. No Git, cada commit é esse ponto de salvamento imutável.
  • O Universo Paralelo (Branch): Se você quer experimentar uma magia nova arriscada sem perder seu progresso no jogo principal, você cria um "clone da realidade". Se a experiência der certo, você funde essa realidade com a principal (Merge). Se der errado, você simplesmente descarta o universo sem danificar nada.
  • O Livro de Histórias (Log): Cada decisão tomada no código tem data, autor e motivo registrado. Ninguém precisa adivinhar por que uma linha de código foi escrita há 2 anos.

2. Git Local vs. Plataformas na Nuvem (GitHub & GitLab)

Um erro clássico de quem está iniciando na área é confundir o Git com o GitHub ou GitLab. Eles não são a mesma coisa:

Aspecto Git (Ferramenta Local) GitHub / GitLab (Plataformas em Nuvem)
O que é? O motor de software instalado no seu computador. Plataformas web que hospedam repositórios Git remotos na nuvem.
Onde roda? 100% offline no seu terminal / máquina de desenvolvimento. Em servidores corporativos ou servidores na nuvem (SaaS).
Função Principal Rastrear arquivos, criar branches, comitar histórico localmente. Colaboração em equipe, code review, automações e segurança.
Recursos Chave git commit, git branch, git merge, git log Pull Request / Merge Request, Issues, Kanban, CI/CD Pipelines.

GitHub vs. GitLab: Terminologia Equivalente

  • GitHub Pull Request (PR) = GitLab Merge Request (MR): Uma solicitação formal para mesclar o código da sua branch de desenvolvimento para a branch principal, onde colegas revisam o código linha por linha antes de aceitar.
  • GitHub Actions = GitLab CI/CD: Robôs automatizados configurados para rodar testes unitários, checar regras de estilo (linting) e realizar o deploy automático nos servidores de homologação ou produção sempre que um código novo é aprovado.

3. A Arquitetura das 4 Zonas do Git

Para dominar o Git, você não deve apenas decorar comandos: você precisa enxergar onde o seu arquivo está fisicamente dentro das 4 camadas fundamentais.

Diagrama: O Fluxo de Dados entre as 4 Camadas do Git
  • Working Directory: É a pasta onde você trabalha diariamente na sua IDE (VS Code, IntelliJ, etc.). O arquivo aqui está modificado (Modified) ou não rastreado (Untracked).
  • Staging Area (Index): É a antessala do commit. Você escolhe exatamente o que vai entrar no próximo pacote de salvamento usando git add. Isso permite criar commits limpos e atômicos.
  • Repositório Local (.git): O banco de dados interno na sua máquina onde os commits são salvos em definitivo. Se a internet cair, você continua commitando normalmente aqui.
  • Repositório Remoto: O servidor centralizado na nuvem (GitHub, GitLab) onde os outros membros da equipe buscam e enviam códigos.

4. Comandos Essenciais do Dia a Dia

4.1 Conexões Remotas (Gerenciando a Ponte Local ➔ Nuvem)

Comandos para conectar seu código do computador com a nuvem ou transferir projetos existentes.

Bash / Terminal 
# 1. Clonar um repositório existente na nuvem para seu computador
git clone https://github.com/organizacao/projeto-backend.git

# 2. Listar todas as conexões remotas configuradas no seu projeto atual
git remote -v

# 3. Adicionar uma nova conexão remota (geralmente chamada 'origin')
git remote add origin https://gitlab.com/organizacao/meu-novo-repo.git

# 4. Remover / Cortar uma conexão remota existente
git remote remove origin
# (ou a sintaxe abreviada: git remote rm origin)

# 5. Alterar a URL de uma conexão remota que mudou de endereço
git remote set-url origin https://github.com/organizacao/novo-endereco.git

4.2 Ciclo de Vida do Commit (Salvando o Trabalho)

Bash / Terminal 
# 1. Ver o estado atual (quais arquivos foram criados, alterados ou deletados)
git status

# 2. Ver as alterações linha a linha feitas nos arquivos antes de adicionar ao palco
git diff

# 3. Adicionar um arquivo específico para a Staging Area
git add src/services/user.service.ts

# 4. Adicionar TODAS as alterações de uma vez só
git add .

# 5. Criar o ponto de salvamento (commit) com uma mensagem descritiva padronizada
git commit -m "feat(auth): adiciona validação de token JWT no login"

# 6. Enviar os commits locais para o servidor remoto (primeira vez)
git push -u origin feature/login-jwt

# 7. Atualizar sua branch com as novidades que seus colegas enviaram
git pull origin main

4.3 Gestão de Branches (Linhas de Desenvolvimento Paralelo)

Bash / Terminal 
# 1. Listar todas as branches locais
git branch

# 2. Criar uma nova branch e entrar nela imediatamente (Método Moderno)
git switch -c feature/calculo-tarifa

# (Método Clássico equivalente):
git checkout -b feature/calculo-tarifa

# 3. Trocar entre branches já existentes
git switch main
# ou: git checkout main

# 4. Deletar uma branch local que já foi mesclada e finalizada
git branch -d feature/calculo-tarifa

# 5. Forçar a exclusão de uma branch local mesmo se não foi mesclada
git branch -D feature/calculo-tarifa

4.4 Mesclando Códigos: Merge vs. Rebase

Quando sua funcionalidade está pronta, você precisa integrar seu código com a linha principal.

Bash / Terminal 
# Cenário: Você quer trazer o código da 'feature/nova-api' para dentro da 'main'

# 1. Vá para a branch de destino
git switch main

# 2. Atualize a branch de destino com o que está na nuvem
git pull origin main

# 3. Execute o merge unindo a branch da funcionalidade
git merge feature/nova-api

# O Git criará um "Merge Commit" unindo os dois históricos de forma explícita.
⚠️ Atenção: Merge Local vs. Pull Request / Merge Request

Em ambientes profissionais, você raramente fará git merge direto na sua máquina para a branch principal (main ou master). O fluxo correto é:

  1. Você envia sua branch para a nuvem: git push origin feature/minha-tela.
  2. Abre um Pull Request (GitHub) ou Merge Request (GitLab) pelo navegador.
  3. Colegas de time revisam o código, a esteira de CI/CD roda os testes, e o botão de Merge é clicado na plataforma web.

5. Viagem no Tempo: Desfazendo Alterações e Restaurando Versões

Erros acontecem. A grande vantagem do Git é que quase nada é irrecuperável se foi commitado. Veja as 4 ferramentas para voltar atrás:

Comando O que faz? Quando Usar? Impacto / Risco
git restore <arquivo> Descarta as alterações locais não comitadas de um arquivo no Working Directory. Fiz besteira no código hoje e quero voltar para a versão do último commit. Médio (Descarta alterações locais não salvas)
git checkout <hash> Move sua visão (HEAD) para um commit passado específico em modo de leitura (Detached HEAD). Quero compilar e ver como o sistema funcionava no commit a1b2c3d sem alterar o código atual. Zero (Modo leitura, seguro)
git revert <hash> Cria um novo commit que faz exatamente o inverso das alterações do commit especificado. O código já subiu para a nuvem/produção e causou um bug. Preciso desfazer sem reescrever a história. Seguríssimo (Ideal para branches compartilhadas)
git reset --soft <hash> Desfaz os commits até aquele ponto, mas mantém todo o código modificado na Staging Area. Fiz um commit antes da hora ou errei o texto e quero agrupar tudo em um novo commit. Baixo (Nenhum código é perdido)
git reset --hard <hash> Apaga completamente todos os commits e alterações do disco até o commit escolhido. Quero jogar tudo o que fiz fora e voltar a estaca zero de um commit passado. Perigo Alto (Apaga código permanentemente)
Bash / Exemplos Práticos 
# 1. Descobrir a identificação (Hash) dos commits anteriores
git log --oneline -n 5
# Saída:
# 7f8a9b1 fix(auth): corrige expiração de sessão
# 3c4d5e6 feat(api): adiciona rota de relatórios
# 9a8b7c6 feat(db): conecta ao banco PostgreSQL

# 2. Desfazer o commit '3c4d5e6' criando um commit de reversão (SEGURO PARA REPOSITÓRIOS PÚBLICOS):
git revert 3c4d5e6
git push origin main

# 3. Voltar atrás apenas localmente mantendo o código no seu editor (para ajustar e recommitar):
git reset --soft HEAD~1

# 4. Descartar alterações de um arquivo antes de adicionar ao git:
git restore src/app.controller.ts

6. Tags de Ambientes: Produção, Homologação e Desenvolvimento

Uma Tag no Git é um marcador de posição fixo e imutável que aponta para um commit específico no histórico. Enquanto as branches se movem continuamente para frente a cada novo commit, as tags ficam paradas para sempre naquele exato ponto.

Elas são a espinha dorsal de deploy contínuo (CI/CD) e de rastreabilidade de bugs no mercado profissional:

Diagrama: Estratégia de Branches e Tags por Ambiente (Dev ➔ Homolog ➔ Prod)
Ambiente Padrão de Nomeclatura de Tag Propósito e Quem Utiliza Gatilho no CI/CD
1. Desenvolvimento (DEV) dev-latest ou tags de build automático (ex: v1.2.0-alpha.1, build-20261002-42) Usado exclusivamente por desenvolvedores para testar integrações entre microsserviços e banco de dados local/remoto compartilhado. Qualquer merge na branch develop ou push de tag dev-* sobe nos containers de teste interno.
2. Homologação / Staging (HML) v1.2.0-rc.1, v1.2.0-beta.2
(RC = Release Candidate)		 Ambiente idêntico à produção em hardware e dados mascarados. Utilizado pela equipe de QA (Testes), Tech Leads e Clientes/Usuários finais para homologar antes da liberação oficial. Ao criar uma tag *-rc.*, o CI/CD gera a imagem Docker e publica no ambiente de Homologação.
3. Produção (PROD) v1.0.0, v1.2.0, v1.2.1
(Seguindo estritamente SemVer)		 O ambiente real onde os usuários e clientes finais estão operando. O código aqui é considerado estável, auditado e imutável. A publicação da tag vX.Y.Z dispara o pipeline de produção que atualiza os clusters de Kubernetes sem tempo de inatividade.

6.1 Padrão de Versionamento Semântico (SemVer: vMAJOR.MINOR.PATCH)

  • MAJOR (v2.0.0): Alterações incompatíveis na API (quebra de contratos antigos).
  • MINOR (v1.1.0): Adição de novas funcionalidades mantendo compatibilidade com o que já existia.
  • PATCH (v1.0.1): Correções rápidas de bugs emergenciais (hotfixes) sem novas funcionalidades.
Bash / Como Criar e Gerenciar Tags 
# 1. Listar todas as tags do repositório
git tag

# 2. Criar uma Tag Anotada (com autor, data e mensagem descritiva - PADRÃO DE PRODUÇÃO)
git tag -a v1.2.0 -m "Release v1.2.0: Módulo de integração com bilhetagem e GPS"

# 3. Criar uma Tag de Homologação (Release Candidate)
git tag -a v1.2.0-rc.1 -m "Candidato a release para validação da equipe de QA"

# 4. Criar tag para um commit que ficou no passado (especificando o hash)
git tag -a v1.0.1 9a8b7c6 -m "Hotfix emergencial aplicado no cálculo de frota"

# 5. IMPORTANTE: 'git push' convencional NÃO envia tags! Você precisa enviar explicitamente:
# Enviar uma tag específica:
git push origin v1.2.0

# Ou enviar todas as novas tags locais de uma vez:
git push origin --tags

# 6. Deletar uma tag local e na nuvem (caso tenha criado por engano):
git tag -d v1.2.0-rc.1
git push origin --delete v1.2.0-rc.1

7. Padronização de Nomenclatura (Conventional Commits & Branches)

Em um projeto profissional compartilhado, a mensagem de commit não serve apenas para "cumprir tabela". Ela gera documentação viva, changelogs automáticos e permite entender a evolução do produto. O padrão adotado pela indústria é o Conventional Commits:

Formato Oficial da Mensagem
<tipo>(<escopo opcional>): <descrição sucinta no presente>
Prefixo Propósito Exemplo de Mensagem
feat Adição de uma nova funcionalidade no sistema. feat(auth): adiciona autenticação de usuários via JWT
fix Correção de um bug ou comportamento incorreto. fix(api): corrige estouro de memória no cálculo de rotas
docs Alterações exclusivamente em documentação (README, Swagger, etc.). docs: documenta variáveis de ambiente no manual de onboarding
style Ajustes de formatação, ponto e vírgula, indentação (sem alterar lógica). style: formata arquivos com prettier e eslint
refactor Reescrita interna de código que não adiciona recurso nem corrige bug. refactor(service): desacopla lógica de envio de email
perf Otimização de performance de código ou consultas SQL. perf(db): adiciona índice na coluna cd_linha para busca rápida
test Criação ou ajuste de baterias de testes unitários ou e2e. test(user): adiciona casos de teste para senha fraca
chore Tarefas rotineiras de manutenção, build, dockerfile ou dependências. chore(deps): atualiza versão do node para 20-alpine
ci Alterações nos scripts e configurações de pipelines (GitHub Actions, GitLab CI). ci: adiciona etapa de validação de testes antes do deploy

7.1 Padrão de Nomenclatura para Branches

  • feature/nome-da-funcionalidade: Ex: feature/login-govbr, feature/exportacao-csv
  • fix/nome-do-bug: Ex: fix/calculo-tarifa-feriado
  • hotfix/correcao-urgente: Ex: hotfix/vazamento-memoria-prod (correção direta que vai para a tag de patch)
  • refactor/modulo-alterado: Ex: refactor/repositorios-typeorm

8. As 6 Regras de Ouro em Repositórios Compartilhados

🚨 REGRA 1: NUNCA dê commit ou push direto na 'main' ou 'master'

A branch principal é sagrada. Ela reflete código que pode ir para produção a qualquer instante. Todo o trabalho deve ser feito em branches separadas e incorporado via Pull Request / Merge Request com aprovação de pares.

⚠️ REGRA 2: Cuidado Extremo com 'git push --force' (-f)

O push --force reescreve a história remota. Se você rodar esse comando em uma branch que outros desenvolvedores estão usando, você poderá apagar commits de outras pessoas permanentemente. Regra prática: Nunca use force push em branches públicas.

  • 3. Faça Commits Atômicos: Não acumule 3 dias de trabalho para fazer um único commit com 50 arquivos alterados chamado "ajustes gerais". Faça commits pequenos, cada um resolvendo um problema único e isolado.
  • 4. Atualize sua branch logo no início do expediente: Antes de começar a programar, vá na branch principal, dê git pull, volte para a sua branch e traga as novidades (git merge main). Resolver conflitos pequenos diariamente evita ter que resolver centenas de conflitos gigantes no fim do mês.
  • 5. Não comite arquivos gerados ou segredos: Nunca suba pastas node_modules/, arquivos dist/, arquivos .env com senhas de banco ou chaves de API. Configure sempre um arquivo .gitignore robusto.
  • 6. Revise seu próprio Diff antes de abrir PR/MR: Antes de solicitar revisão para o Tech Lead ou colega, leia as suas alterações na interface do GitHub/GitLab. Você frequentemente encontrará console.log esquecidos, códigos comentados e formatações desnecessárias.

9. Base de Conhecimento e Cenários Rápidos ("O que fazer quando...?")

Guia prático para você consultar rapidamente na hora do desespero ou da dúvida no trabalho.

✏️ 1. Errei a mensagem do último commit que fiz (e ainda NÃO dei push)

Fácil / Seguro

Você comitou com um erro de digitação ou esqueceu de seguir o padrão Conventional Commits (ex: colocou "ajuste" em vez de "fix(rotas): corrige cálculo de tarifa").

BASH / TERMINAL 
# Altera a mensagem do último commit sem duplicar no histórico
git commit --amend -m "fix(rotas): corrige cálculo de tarifa no itinerário"
💡
Dica do Supervisor: Enquanto o commit for puramente local e não tiver sido enviado com git push, o --amend é 100% inofensivo e limpa o seu histórico antes do Code Review.

📦 2. Fiz o commit, mas esqueci de incluir um arquivo importante nele

Fácil / Seguro

Você salvou o commit e percebeu que um arquivo de teste, migration ou rota ficou de fora do git add. Não precisa criar um commit novo "esqueci arquivo"!

BASH / TERMINAL 
# 1. Adicione o arquivo que ficou para trás
git add src/modules/linha/linha.service.spec.ts

# 2. Incorpore silenciosamente no commit anterior mantendo a mesma mensagem
git commit --amend --no-edit
💡
Dica do Supervisor: A flag --no-edit instrui o Git a reaproveitar a mensagem exata do commit anterior sem abrir o editor de texto interativo no terminal.

🌿 3. Comecei a codificar na branch 'main' por engano (mas ainda NÃO comitei nada)

Atenção

Você abriu o VS Code, escreveu várias linhas de código e quando rodou git status percebeu que está na branch main! Como migrar todo esse código para a branch correta sem perder nada?

BASH / TERMINAL 
# Cria a branch da sua tarefa e migra todas as alterações pendentes intactas
git switch -c feature/SUTINF-1204-painel-monitoramento

# Agora sim, adicione e comite na branch correta
git add .
git commit -m "feat(painel): implementa grid de monitoramento de frotas"
💡
Dica do Supervisor: Como as alterações estavam apenas na sua Working Tree (não salvas em commit), o Git preserva o seu trabalho e o transporta automaticamente para a nova branch criada.

⚡ 4. Preciso trocar de branch agora para ajudar um colega, mas meu código está incompleto e quebrado

Uso Diário / Produtividade

Você está no meio de um raciocínio complexo, com erros de TypeScript na tela, e o Tech Lead pede para você testar uma branch de homologação. Como não perder seu rascunho sem criar commits sujos?

BASH / TERMINAL 
# 1. Guarda tudo em uma gaveta segura e limpa a área de trabalho
git stash save "rascunho: filtros do mapa em andamento"

# 2. Navegue até a outra branch e faça o teste solicitado
git switch homologacao-semob
git pull origin homologacao-semob

# 3. Terminou? Volte para sua branch de desenvolvimento
git switch feature/minha-tarefa

# 4. Abra a gaveta e restaure suas alterações exatamente de onde parou
git stash pop
💡
Dica do Supervisor: O git stash pop reaplica suas mudanças e remove o item da gaveta. Para verificar seus stashes acumulados, use git stash list.

🚨 5. Enviei um commit com BUG para o GitLab / Produção e preciso anular IMEDIATAMENTE

Crítico / Produção

Seu Merge Request foi aprovado e integrado, mas gerou instabilidade no servidor. NUNCA use git reset ou push -f em branches públicas! Crie um commit reverso de anulação cirúrgica.

BASH / TERMINAL 
# 1. Localize o hash do commit problemático
git log --oneline -n 3
# Exemplo de saída: 4f8a1bc fix(auth): altera validacao de token jwt

# 2. Crie um commit que desfaz exatamente as linhas daquele commit
git revert 4f8a1bc --no-edit

# 3. Envie a reversão para o repositório remoto com segurança
git push origin main
💡
Dica do Supervisor: O git revert é a prática recomendada em engenharia corporativa porque preserva a rastreabilidade e auditoria de incidentes, sem corromper a cópia dos demais desenvolvedores.

⚔️ 6. Deu Conflito de Merge (CONFLICT). Como resolver sem pânico?

Resolução de Conflito

O conflito ocorre quando você e outro desenvolvedor alteraram as mesmas linhas do mesmo arquivo em momentos diferentes. O Git não sabe qual linha deve prevalecer e solicita a intervenção humana.

  1. Abra o VS Code: ele destacará os blocos conflitantes entre <<<<<<< HEAD (seu código) e >>>>>>> branch (código remoto).
  2. Use os botões de atalho no topo do editor: Accept Current Change, Accept Incoming Change ou edite manualmente combinando as duas lógicas.
  3. Remova todos os marcadores de conflito, salve o arquivo e execute:
BASH / TERMINAL 
# Marca os arquivos conflitantes como resolvidos
git add src/services/itinerario.service.ts

# Conclui a operação de merge
git commit -m "chore: resolve conflito de merge com a branch main"
💡
Dica do Supervisor: Para evitar conflitos assustadores, atualize sua branch frequentemente trazendo as novidades da main no início de todo turno de trabalho.

🍒 7. Quero pegar apenas UM commit específico de outra branch sem mesclar ela inteira

Avançado / Cirúrgico

Um colega consertou uma função utilitária na branch dele, mas a branch dele ainda contém outros recursos inacabados. Você quer puxar exclusivamente aquele conserto para a sua branch.

BASH / TERMINAL 
# 1. Certifique-se de estar na SUA branch
git switch feature/minha-tela

# 2. Aplique cirurgicamente o commit desejado pelo hash
git cherry-pick 9c3e21a
💡
Dica do Supervisor: O cherry-pick replica o diff exato daquele commit criando um novo hash na sua branch. Use com moderação para não fragmentar o fluxo do Git.

🧹 8. Modifiquei um arquivo localmente, fiz besteira e quero voltar ao original

Fácil / Seguro

Você fez testes em um arquivo local, bagunçou a estrutura e quer descartar todas as alterações não comitadas daquele arquivo específico, voltando ao estado limpo.

BASH / TERMINAL 
# Restaura um arquivo específico para a versão do último commit
git restore src/app.controller.ts

# Ou restaura TODOS os arquivos alterados da pasta inteira
git restore .
💡
Dica do Supervisor: O git restore é o substituto moderno e seguro do antigo git checkout -- arquivo, tornando a intenção clara no terminal.
