1. Visão Geral da Arquitetura e Stack Tecnológico

O backend do ecossistema SISMOB foi concebido para atender a operações de transporte público e mobilidade urbana com alta confiabilidade, concorrência massiva, blindagem de segurança contra injeção de código e estrita aderência a contratos de API RESTful.

1.1 Stack Tecnológico

Camada / Função Tecnologia Adotada Justificativa Técnica
Linguagem TypeScript 5.7+ sobre Node.js 20+ / 22 LTS Tipagem estática rigorosa em tempo de compilação, prevenção de bugs de runtime e autocompletion avançado.
Framework Principal NestJS 11 (@nestjs/core, @nestjs/common) Arquitetura corporativa opinionada baseada em Injeção de Dependências (IoC), módulos independentes e ciclo de vida padronizado.
Camada HTTP Express (@nestjs/platform-express) Plataforma HTTP robusta, consolidada e com amplo ecossistema de interceptores e middlewares.
ORM & Query Builder TypeORM 0.3.x (@nestjs/typeorm) Abstração relacional híbrida: mapeamento declarativo de entidades (Active Record / Data Mapper) e execução de SQL nativo parametrizado.
Banco de Dados Relacional PostgreSQL 15 (com extensão PostGIS) / Oracle Database Confiabilidade ACID, suporte a indexação geográfica e compatibilidade com os legados corporativos do GDF.
Validação de Payload class-validator + class-transformer Validação declarativa por anotações em runtime com sanitização de campos desconhecidos (whitelist).
Autenticação & Segurança JWT (JSON Web Token) via @nestjs/jwt + Bcrypt Tokens de acesso compactos, stateless, com validação criptográfica em guardas de rota (JwtAuthGuard).

Containerização & Deploy Docker, Docker Compose e Kubernetes (K8s) Portabilidade total de desenvolvimento e deploy declarativo com escalabilidade horizontal em produção.

1.2 Padrão Arquitetural Adotado

O projeto adota uma Arquitetura em Camadas (Layered Architecture) com Modularidade por Domínio e Inversão de Controle / Injeção de Dependências (IoC / DI).

As camadas seguem o princípio da responsabilidade única (SRP) e da dependência unidirecional descendente: cada camada só pode invocar serviços da camada imediatamente inferior, nunca da superior e nunca pulando etapas:

[ Cliente HTTP ]
       │
       ▼
[ Camada de Entrada ] ──────► Controllers, DTOs & Swagger
       │
       ▼
[ Camada de Domínio ] ──────► Services & Exceções de Negócio
       │
       ▼
[ Camada de Persistência ] ──► Repositories (TypeORM / SQL Parametrizado)
       │
       ▼
[ Camada de Dados ] ────────► Entidades & Banco de Dados (PostgreSQL / Oracle)
REGRA IMPORTANTE

Regra Fundamental de Isolamento:

  • O Controller nunca acessa o banco de dados diretamente;
  • O Repository nunca conhece objetos de requisição HTTP (Request, Response) e não contém regras de validação de negócio;
  • O Service é o único detentor das decisões, orquestrações e regras do domínio.

1.3 Ciclo de Vida de uma Requisição (Request Lifecycle)

O fluxo detalhado percorrido por qualquer requisição que chega à API segue rigorosamente a esteira de execução do NestJS:

3.2 Uso de DTOs e Validação de Entrada

Todo dado que ingressa na API por meio da Query String, Route Params ou Body DEVE ser tipado e validado por um DTO.

O projeto utiliza o ValidationPipe do NestJS configurado globalmente no src/main.ts:

app.useGlobalPipes(
  new ValidationPipe({
    whitelist: true,            // Remove automaticamente qualquer propriedade não declarada no DTO
    forbidNonWhitelisted: true, // Lança HTTP 400 se o cliente enviar propriedades estranhas
    transform: true,            // Converte strings em tipos primitivos automaticamente (ex: '123' -> 123)
  }),
);

Exemplo de DTO com Validação e Swagger:

import { IsString, IsNotEmpty, IsOptional, MaxLength, Matches } from 'class-validator';
import { ApiProperty, ApiPropertyOptional } from '@nestjs/swagger';

export class FilterLinhaDto {
  @ApiPropertyOptional({
    description: 'Código oficial da linha no padrão SEMOB',
    example: '0.108',
  })
  @IsOptional()
  @IsString({ message: 'O código da linha deve ser uma string.' })
  @MaxLength(8, { message: 'O código da linha não pode exceder 8 caracteres.' })
  codigo?: string;

  @ApiPropertyOptional({
    description: 'Descrição ou itinerário da linha',
    example: 'W3 Norte',
  })
  @IsOptional()
  @IsString({ message: 'A descrição deve ser um texto válido.' })
  @MaxLength(255, { message: 'A descrição não pode exceder 255 caracteres.' })
  descricao?: string;
}

POST 200 OK Operações de processamento, comandos ou login Retorna tokens ou confirmação da operação ({ access_token: ... })

4. Tratamento de Erros e Middlewares

4.1 Filtro Global de Exceções (AllExceptionsFilter)

Nenhuma exceção não tratada deve vazar para o cliente como stack trace de Node.js. O projeto conta com o AllExceptionsFilter (src/filters/all-exceptions.filter.ts), ativado globalmente no main.ts.

Contrato Único de Resposta de Erro:

Toda resposta com código de status >= 400 devolve obrigatoriamente a seguinte estrutura JSON:

{
  "statusCode": 404,
  "timestamp": "2026-10-01T16:50:00.000Z",
  "path": "/api/veiculos/999",
  "method": "GET",
  "message": "Veículo com identificador '999' não foi encontrado."
}

Implementação do Filtro:

@Catch()
export class AllExceptionsFilter implements ExceptionFilter {
  private readonly logger = new Logger(AllExceptionsFilter.name);

  catch(exception: unknown, host: ArgumentsHost) {
    const ctx = host.switchToHttp();
    const response = ctx.getResponse<Response>();
    const request = ctx.getRequest<Request>();

    const status =
      exception instanceof HttpException
        ? exception.getStatus()
        : HttpStatus.INTERNAL_SERVER_ERROR;

    const message =
      exception instanceof HttpException
        ? (exception.getResponse() as any).message || exception.message
        : 'Internal server error';

    const errorResponse = {
      statusCode: status,
      timestamp: new Date().toISOString(),
      path: request.url,
      method: request.method,
      message: message,
    };

    if (status === HttpStatus.INTERNAL_SERVER_ERROR) {
      this.logger.error(
        `${request.method} ${request.url}`,
        exception instanceof Error ? exception.stack : 'Unknown Error',
      );
    } else {
      this.logger.warn(
        `${request.method} ${request.url} - Status: ${status} - Message: ${JSON.stringify(message)}`,
      );
    }

    response.status(status).json(errorResponse);
  }
}

Nunca lance throw new Error('mensagem') dentro dos Services. O projeto disponibiliza classes semânticas derivadas de HttpException:

5. Acesso a Dados (Banco de Dados)

5.1 Decisão Arquitetural: ORM (Entity) vs. SQL Nativo Parametrizado

Para suportar a alta demanda de transações e relatórios da SEMOB-DF mantendo produtividade no dia a dia, adotamos a seguinte regra:

                                 Qual é o tipo de operação?
                                             │
                      ┌──────────────────────┴──────────────────────┐
                      ▼                                             ▼
          [ Operações de CRUD ]                         [ Consultas Complexas ]
      • Criação, edição e deleção                   • Múltiplos JOINS (3+ tabelas)
      • Busca simples por Chave Primária            • Agregações pesadas (SUM, COUNT, GROUP BY)
      • Validação estrutural de tipos               • Queries dinâmicas com muitos filtros
                      │                                             │
                      ▼                                             ▼
          Use TypeORM Entity / Methods                  Use SQL Nativo Parametrizado
          (this.save, this.findOne)                     (this.dataSource.query)
  • Por que usar TypeORM nos CRUDs?
    Acelera o desenvolvimento, garante tipagem forte, simplifica inserções e mantém histórico de auditoria automatizado (CreateDateColumn, UpdateDateColumn).
  • Por que usar SQL Nativo nas Consultas Complexas?
    Performance extrema (elimina o overhead de hydration do ORM), permite utilizar recursos específicos do PostgreSQL/Oracle (PostGIS, índices funcionais, CTEs) e oferece legibilidade total para os engenheiros de dados.

5.2 Blindagem Rígida Contra SQL Injection

ALERTA DE SEGURANÇA / CUIDADO

TOLERÂNCIA ZERO PARA CONCATENAÇÃO DE SQL: Sob nenhuma circunstância utilize concatenação (+, ${var}) para inserir valores externos no comando SQL.

O padrão oficial para consultas dinâmicas utiliza queries parametrizadas com arrays de valores separados:

// ✅ PADRÃO CORRETO (SEGURO CONTRA SQL INJECTION):
async findByFilters(codigo?: string, descricao?: string): Promise<Linha[]> {
  let sql = `
    SELECT 
      id_linha as "id", 
      cd_linha as "codigo", 
      tx_linha as "descricao", 
      vl_tarifa as "valorTarifa"
    FROM dados_mobilidade.tab_linha 
    WHERE 1=1
  `;

  const params: any[] = [];

  if (codigo) {
    // No PostgreSQL nativo usamos $1, $2, $3...
    sql += ` AND cd_linha = $${params.length + 1}`;
    params.push(codigo);
  }

  if (descricao) {
    sql += ` AND tx_linha ILIKE $${params.length + 1}`;
    params.push(`%${descricao}%`);
  }

  // O driver do PostgreSQL (pg) substitui os parâmetros com escape seguro
  return this.dataSource.query(sql, params);
}

// ❌ CÓDIGO VULNERÁVEL (ESTRITAMENTE PROIBIDO):
const sql = `SELECT * FROM tab_linha WHERE cd_linha = '` + codigo + `'`; // VULNERÁVEL A SQL INJECTION!

5.3 Modelagem de Entidades e Estratégia de Migrations/Seeds

Convenções de Mapeamento:

  1. Sempre defina explicitamente o nome da tabela física e do schema (@Entity({ name: 'tab_linha', schema: 'dados_mobilidade' })).
  2. Mapeie os nomes de colunas do banco (snake_case) para propriedades em camelCase na classe TypeScript.
  3. Utilize a classe abstrata BaseEntity (src/utils/Base.ts) para incluir automaticamente colunas de auditoria temporal.

Políticas de Sincronização:

  • Ambiente Local (development): DB_SYNCHRONIZE=true pode ser utilizado para acelerar a prototipagem inicial.
  • Ambientes de Homologação e Produção: DB_SYNCHRONIZE=false é obrigatório. Modificações de schema devem ser aplicadas via scripts SQL versionados ou migrations controladas.
  • Seeds Automatizados (SeedService): O SeedService (src/service/Seed.ts) executa arquivos SQL declarativos no evento onApplicationBootstrap() apenas se a tabela correspondente estiver vazia, garantindo idempotência.

6. Tutorial Prático para Estagiários: Do Zero ao Endpoint Completo

6.1 Passo 1: Criação da Entidade de Banco

Crie o arquivo src/entity/Veiculo.ts:

import { Entity, PrimaryGeneratedColumn, Column, CreateDateColumn } from 'typeorm';

@Entity({ name: 'tab_veiculo', schema: 'dados_mobilidade' })
export class Veiculo {
  @PrimaryGeneratedColumn({ name: 'id_veiculo' })
  id: number;

  @Column({ name: 'nr_prefixo', length: 10, unique: true })
  prefixo: string; // Ex: '115201'

  @Column({ name: 'nr_placa', length: 8, unique: true })
  placa: string; // Ex: 'ABC1D23'

  @Column({ name: 'ds_modelo', length: 100 })
  modelo: string; // Ex: 'Caio Millennium IV'

  @Column({ name: 'st_ativo', type: 'boolean', default: true })
  ativo: boolean;

  @CreateDateColumn({ name: 'dataregistro' })
  dataRegistro: Date;
}

6.3 Passo 3: Criação do Repositório Especializado

Crie o arquivo src/repository/Veiculo.ts:

import { Injectable } from '@nestjs/common';
import { DataSource, Repository } from 'typeorm';
import { Veiculo } from '../entity/Veiculo';

@Injectable()
export class VeiculoRepository extends Repository<Veiculo> {
  constructor(private dataSource: DataSource) {
    super(Veiculo, dataSource.createEntityManager());
  }

  /**
   * Consulta parametrizada com alta performance para listagens dinâmicas
   */
  async findByFilters(prefixo?: string, ativo?: boolean): Promise<Veiculo[]> {
    let sql = `
      SELECT 
        id_veiculo as "id",
        nr_prefixo as "prefixo",
        nr_placa as "placa",
        ds_modelo as "modelo",
        st_ativo as "ativo",
        dataregistro as "dataRegistro"
      FROM dados_mobilidade.tab_veiculo
      WHERE 1=1
    `;

    const params: any[] = [];

    if (prefixo) {
      sql += ` AND nr_prefixo LIKE $${params.length + 1}`;
      params.push(`%${prefixo}%`);
    }

    if (ativo !== undefined) {
      sql += ` AND st_ativo = $${params.length + 1}`;
      params.push(ativo);
    }

    sql += ` ORDER BY nr_prefixo ASC`;

    return this.dataSource.query(sql, params);
  }
}

6.4 Passo 4: Implementação do Service com Regras de Negócio

Crie o arquivo src/service/Veiculo.ts:

import { Injectable } from '@nestjs/common';
import { VeiculoRepository } from '../repository/Veiculo';
import { Veiculo } from '../entity/Veiculo';
import { CreateVeiculoDto, FilterVeiculoDto } from '../dto/Veiculo';
import { EntityNotFoundException } from '../exceptions/entity-not-found.exception';
import { EntityAlreadyExistsException } from '../exceptions/entity-already-exists.exception';

@Injectable()
export class VeiculoService {
  constructor(private readonly veiculoRepository: VeiculoRepository) {}

  async listar(filters: FilterVeiculoDto): Promise<Veiculo[]> {
    return this.veiculoRepository.findByFilters(filters.prefixo, filters.ativo);
  }

  async buscarPorId(id: number): Promise<Veiculo> {
    const veiculo = await this.veiculoRepository.findOne({ where: { id } });
    if (!veiculo) {
      throw new EntityNotFoundException('Veículo', id);
    }
    return veiculo;
  }

  async criar(dto: CreateVeiculoDto): Promise<Veiculo> {
    // 1. Regra de Negócio: Não permitir duplicidade de placa
    const placaExistente = await this.veiculoRepository.findOne({ where: { placa: dto.placa } });
    if (placaExistente) {
      throw new EntityAlreadyExistsException('Veículo', 'placa', dto.placa);
    }

    // 2. Regra de Negócio: Não permitir duplicidade de prefixo
    const prefixoExistente = await this.veiculoRepository.findOne({ where: { prefixo: dto.prefixo } });
    if (prefixoExistente) {
      throw new EntityAlreadyExistsException('Veículo', 'prefixo', dto.prefixo);
    }

    // 3. Persistência via ORM
    const novoVeiculo = this.veiculoRepository.create(dto);
    return this.veiculoRepository.save(novoVeiculo);
  }
}

6.5 Passo 5: Criação do Controller e Documentação OpenAPI

Crie o arquivo src/controller/Veiculo.ts:

import { Controller, Get, Post, Body, Param, Query, UseGuards, HttpStatus, HttpCode } from '@nestjs/common';
import { ApiTags, ApiOperation, ApiBearerAuth, ApiResponse } from '@nestjs/swagger';
import { VeiculoService } from '../service/Veiculo';
import { CreateVeiculoDto, FilterVeiculoDto } from '../dto/Veiculo';
import { JwtAuthGuard } from '../guards/Jwt';

@ApiTags('Veículos')
@ApiBearerAuth()
@UseGuards(JwtAuthGuard)
@Controller('veiculos')
export class VeiculoController {
  constructor(private readonly veiculoService: VeiculoService) {}

  @Get()
  @ApiOperation({ summary: 'Listar veículos com filtros opcionais' })
  @ApiResponse({ status: 200, description: 'Listagem retornada com sucesso.' })
  async listar(@Query() filters: FilterVeiculoDto) {
    return this.veiculoService.listar(filters);
  }

  @Get(':id')
  @ApiOperation({ summary: 'Obter detalhes de um veículo por ID' })
  @ApiResponse({ status: 200, description: 'Veículo localizado.' })
  @ApiResponse({ status: 404, description: 'Veículo não encontrado.' })
  async buscarPorId(@Param('id') id: number) {
    return this.veiculoService.buscarPorId(id);
  }

  @Post()
  @HttpCode(HttpStatus.CREATED)
  @ApiOperation({ summary: 'Cadastrar um novo veículo na frota' })
  @ApiResponse({ status: 201, description: 'Veículo cadastrado com sucesso.' })
  @ApiResponse({ status: 400, description: 'Dados inválidos fornecidos.' })
  @ApiResponse({ status: 409, description: 'Prefixo ou placa já existente.' })
  async criar(@Body() dto: CreateVeiculoDto) {
    return this.veiculoService.criar(dto);
  }
}

7.3 Como Escrever Testes Automatizados

Testes Unitários de Service (Mockando Repositories)

Os testes unitários devem isolar a camada de serviço de qualquer conexão real com o banco de dados. Crie testes com a extensão .spec.ts ao lado do arquivo correspondente:

// Exemplo: src/service/Veiculo.spec.ts
import { Test, TestingModule } from '@nestjs/testing';
import { VeiculoService } from './Veiculo';
import { VeiculoRepository } from '../repository/Veiculo';
import { EntityNotFoundException } from '../exceptions/entity-not-found.exception';

describe('VeiculoService', () => {
  let service: VeiculoService;
  let repository: Partial<Record<keyof VeiculoRepository, jest.Mock>>;

  beforeEach(async () => {
    repository = {
      findOne: jest.fn(),
      findByFilters: jest.fn(),
      save: jest.fn(),
      create: jest.fn(),
    };

    const module: TestingModule = await Test.createTestingModule({
      providers: [
        VeiculoService,
        { provide: VeiculoRepository, useValue: repository },
      ],
    }).compile();

    service = module.get<VeiculoService>(VeiculoService);
  });

  it('deve lançar EntityNotFoundException se o veículo não existir', async () => {
    repository.findOne!.mockResolvedValue(null);

    await expect(service.buscarPorId(999)).rejects.toThrow(EntityNotFoundException);
  });

  it('deve retornar o veículo quando o ID existir', async () => {
    const mockVeiculo = { id: 1, prefixo: '115201', placa: 'ABC1D23' };
    repository.findOne!.mockResolvedValue(mockVeiculo);

    const resultado = await service.buscarPorId(1);
    expect(resultado).toEqual(mockVeiculo);
    expect(repository.findOne).toHaveBeenCalledWith({ where: { id: 1 } });
  });
});

7.4 Checklist Final de Qualidade de Código (DoD)

Antes de abrir um Merge Request (MR) ou submeter seu código para code review, garanta que:

  • A rota possui DTO de entrada com validações do class-validator e documentação Swagger;
  • O Controller não contém nenhuma regra de negócio ou lógica de banco;
  • O Service lança exceções semânticas (EntityNotFoundException, etc.) em vez de erros genéricos;
  • O Repository não utiliza concatenação de strings em comandos SQL;
  • A rota está protegida com @UseGuards(JwtAuthGuard) (a menos que seja deliberadamente pública);
  • O novo módulo foi devidamente importado no src/app.module.ts;
  • O comando npm run lint executa sem nenhum erro ou aviso;
  • Todos os testes unitários (npm test) passam com 100% de sucesso.
